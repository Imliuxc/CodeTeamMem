Paragraph 1: Problem & Importance A code repository records what a software system currently does, never the full story of why it was built that way. In real-world software engineering, critical knowledge routinely lives outside source files: undocumented API edge cases negotiated between frontend and backend developers, unwritten business constraints born from past production outages, and dead-end debugging paths that teammates already ruled out weeks ago. As large language model (LLM) agents evolve from solo coding assistants into collaborative multi-agent engineering teams, this unwritten layer becomes the primary bottleneck. Relying on static documentation fails because code evolves faster than wikis, and informal trade-offs are rarely codified; dumping raw team logs into long-context windows also breaks down as multi-role histories accumulate noise, role-specific jargon, and superseded decisions. What collaborative coding agents truly need is effective teamwork memory—the ability to selectively preserve, translate, and reuse shared project knowledge across specialized roles and long development cycles. Without it, multi-agent teams suffer from collective amnesia: newly onboarded agents violate implicit constraints, teammates re-introduce previously resolved bugs, and agents burn massive communication budgets rediscovering what another role already knows.
Paragraph 2: Challenges Despite its central role in collaborative software development, systematically benchmarking teamwork memory poses three deep, domain-specific challenges. First, entanglement between code and memory: in a real repository, an agent might solve a task purely through static code inspection or general coding priors rather than drawing on teammates' experiences. Ensuring that a task genuinely requires cross-role memory—especially pragmatic intent that cannot be deduced from source code alone—is non-trivial. Second, role asymmetry and evolving consensus: team knowledge is neither uniform nor static. Different roles (e.g., frontend, backend, QA, DevOps) express constraints in different vocabularies, and software decisions constantly mutate as repositories evolve. A hotfix or refactor today can silently invalidate a teammate's architecture rule from last week, turning outdated memory from an asset into an active distractor. Third, the recall-to-execution gap and failure attribution: recalling a teammate's decision in natural language does not guarantee applying it correctly in executable code. When a generated patch fails unit tests, it is difficult to separate memory retrieval failure, cross-role misinterpretation, communication noise, and the underlying LLM's raw coding limitations.

On one side, agent memory benchmarks operate in an execution vacuum. Most evaluate single-agent conversational recall over personal histories. Recent multi-agent memory efforts take important first steps but remain detached from real software utility: COLLABMEM (Wu et al., 2026) probes routing and conflict resolution over predefined interaction traces without executable repositories, while CoMemBench (Zhao et al., 2026) focuses on short-horizon message propagation and isolation across immediate workflow steps rather than long-term accumulation, updating, and cross-role reuse of team knowledge. On the other side, software engineering benchmarks operate in a social vacuum. Repository-level coding benchmarks such as SWE-bench (Jimenez et al., 2024) assume that the issue description and codebase are self-contained, while single-agent coding memory suites like SWE-MeM (Gao et al., 2026) track only an individual agent's past trajectory. Consequently, no existing benchmark evaluates whether natural-language knowledge accumulated across diverse teammates actually translates into verifiable coding gains over evolving repositories.
